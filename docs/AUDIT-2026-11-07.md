# Orbyn platform audit (7 Nov 2026)

**Scope:** `workspace/loyalty-whitelabel` at `main` (c1277db) plus the home-page branch, the live Supabase project `uajxmplssmlhhanbucge` (read-only checks and Supabase's own advisors), and the live Vercel project.
**Method:** code read of all 58 API routes, auth, database layer and the 13 migrations; Supabase security and performance advisors; `npm audit`; lint, typecheck and the test suite. Checklist: the ECC `security-review` playbook (secrets, input validation, auth, rate limits, headers, logging, dependencies).
**Not done:** no penetration test against the live site, no load test, no review of `design/` templates or the Wallet pass artwork.

## Verdict

The base is sound. There is no critical hole: no secrets in git, every input goes through zod, points move only inside locked database functions, sessions are signed and checked in constant time, the Tap webhook re-reads the charge, uploads are checked by their bytes, and 556 tests include cross-tenant tests.

The real risks are at scale and across venues:
1. Owner numbers and the CSV export **stop counting at 1000 rows**.
2. Anyone can **fill a venue's 9000 card codes** by scripting the join form.
3. PINs are unique **across all venues**, and setting a PIN tells you whether it is taken.
4. The email/password sign-in (the developer's way in) has **no brute-force limit** of its own.

## Fix first (in this order)

| # | Fix | Severity | Effort |
|---|---|---|---|
| 1 | Page every big read (summary, export, guest list, search in SQL) | High | S |
| 2 | Database-backed rate limit on join, email sign-in and guest table routes | High | S–M |
| 3 | PINs scoped to a venue; never answer "taken" | High | M |
| 4 | Security headers, error pages, error monitoring | Medium | S |
| 5 | Keep the points history when a guest is erased | Medium | S |

S = up to a day, M = a few days.

## 1. Architecture and code organisation

**Shape:** Next.js 16.4 (App Router, cacheComponents) on Vercel `fra1`, Supabase Postgres 17 in `eu-central-1`, Tap Payments, Apple and Google Wallet. One web app holds the guest pages, staff till, owner app, developer screens and all APIs. Business rules for points live in Postgres functions (`ledger_earn`, `ledger_redeem`, `ledger_undo`, `ledger_pos_sale`); everything else lives in `src/lib`. Strict TypeScript, no real `any`, zod on every route.

### A1. RLS is switched on but has no policies: the app code is the only tenant wall
- **Severity:** Medium
- **Location:** `src/lib/supabase.ts` (service-role client); all 24 tables (Supabase advisor `rls_enabled_no_policy`)
- **Issue:** every query runs with the service-role key, which bypasses RLS. That is safe today because anon is denied everything and each query filters `venue_id` (and `tests/crossTenant.test.ts` / `tableTenant.test.ts` check it). But one missed `.eq("venue_id", …)` in a future route leaks another venue's guests, and the database will not stop it.
- **Recommended fix:** keep the service role, and add one guard so a missed filter fails loudly: route all tenant reads through a helper that requires the venue.
  ```ts
  // src/lib/tenant.ts
  export const forVenue = (venueId: string) => ({
    from: (table: TenantTable) => db().from(table).select().eq("venue_id", venueId),
  });
  ```
  Then add a CI test that greps `src/app/api` for `db().from(` outside allow-listed files. Longer term: sign a short Supabase JWT with a `venue_id` claim and add `using (venue_id = (auth.jwt()->>'venue_id')::uuid)` policies.

### A2. Single-venue assumptions mixed into a multi-venue schema
- **Severity:** Medium
- **Location:** `src/lib/devChat.ts` `bridgeVenue()` (`BRAND_DEFAULT_VENUE`), `src/lib/brand.ts`, the global PIN index (see S3), `src/app/page.tsx`
- **Issue:** the schema supports many venues (and `calabosAdmin` can `add_business`), but sign-in, the CALABOS bridge and branding pick one venue from an env variable. A second venue on the same deployment half-works.
- **Recommended fix:** decide the model and write it down. Either one deployment and one database per client (the `new-client` script suggests this; then drop `add_business`), or true multi-venue (then venue selection at sign-in, per-venue PINs and per-venue branding from the `venues` table).

### A3. The library layer imports from the app layer
- **Severity:** Low
- **Location:** `src/lib/table/qrKit.ts` → `src/app/dev/screens.ts` (`qrPath`); also `src/app/owner/Service.tsx`, `Guests.tsx`
- **Issue:** shared code depends on a developer-screen file, so deleting or moving the dev screens breaks the QR kit.
- **Recommended fix:** move `qrPath` to `src/lib/qr.ts` and import it from there everywhere.

### A4. Developer and sample-data code ship in the production bundle
- **Severity:** Low
- **Location:** `src/lib/fakeDb.ts`, `src/app/dev/*`, `src/app/api/dev/*`
- **Issue:** properly gated (`NODE_ENV !== "production"`, developer session), but it widens the attack surface and bundle.
- **Recommended fix:** keep the gate; add a build-time check that fails if `LOYALTY_FAKE_DB` or `TAP_FAKE` is set in a production build.

## 2. Security and authentication

### S1. Join form has no rate limit; a script can fill a venue
- **Severity:** High
- **Location:** `src/app/api/join/route.ts`, `src/lib/cards.ts` (`createCard`: 4-digit codes, 9000 per venue)
- **Issue:** `POST /api/join` is public with no limit. A loop with made-up emails creates members until the 9000 codes run out ("The venue may be full"), after which no real guest can join. It also fills the guest list with junk.
- **Recommended fix:** a database-backed limit (works across Vercel instances), the same pattern as `pin_attempts`:
  ```sql
  create table rate_hits (bucket text not null, at timestamptz not null default now());
  create index on rate_hits (bucket, at desc);
  ```
  ```ts
  // allow 5 joins per IP per 10 min and 300 per venue per hour
  if (await tooMany(`join:ip:${ipHash}`, 5, 600) || await tooMany(`join:venue:${venue.id}`, 300, 3600)) return fail("too_many", 429);
  ```
  Also widen card codes to 5 or 6 digits for new cards, and add a Vercel Firewall rate-limit rule on `/api/join`.

### S2. Email/password sign-in has no brute-force limit
- **Severity:** High
- **Location:** `src/app/api/staff/login/route.ts`, `src/lib/staffAuth.ts` `signIn()`
- **Issue:** the developer account (full platform access) signs in here. The route itself never counts failures. Supabase Auth's own per-IP limit sees Vercel's server addresses, not the attacker's, so it does not separate callers. Supabase's leaked-password check is also off (advisor `auth_leaked_password_protection`).
- **Recommended fix:** count failures per email and per IP in the database (reuse `pin_attempts` with `who = hmac('login:'+email)`), lock for 15 minutes after 5 failures, turn on leaked-password protection in Supabase Auth, and add TOTP MFA for the developer role.

### S3. PINs are unique across all venues, and "taken" reveals a working PIN
- **Severity:** High (once a second venue exists)
- **Location:** `src/lib/pin.ts` `setPin()` (clash check has no `venue_id`), `signInWithPin()` (global lookup), index `staff_users_pin_lookup_idx` (global unique)
- **Issue:** an owner of venue A who tries PINs in "set PIN" learns from the "taken" answer which PINs belong to someone, possibly at venue B. PIN sign-in then lets them in as that person, because sign-in does not ask for a venue. With 4-digit staff PINs there are only about 9000 possible across the whole platform.
- **Recommended fix:** make PINs unique per venue and ask for the venue at sign-in (the till is already bound to one venue: put the venue slug in the sign-in URL or a device cookie set by the owner). Never let a person choose a PIN: always generate it (`generatePin` exists), retrying on a clash, so "taken" never reaches anyone.
  ```sql
  drop index staff_users_pin_lookup_idx;
  create unique index staff_users_pin_per_venue on staff_users (venue_id, pin_lookup) where pin_lookup is not null;
  ```

### S4. One wrong-PIN counter for the whole platform lets anyone lock everybody out
- **Severity:** Medium
- **Location:** `src/lib/pin.ts` (`OVERALL = 30` per 10 minutes)
- **Issue:** 30 wrong PINs from any mix of addresses pause sign-in for every staff member of every venue for 10 minutes. A script can keep the till locked all evening.
- **Recommended fix:** count the overall limit per venue (after S3) and add a slower back-off rather than a hard stop, for example 1 try per 10 s per venue once over the limit.

### S5. In-memory rate limits do little on Vercel
- **Severity:** Medium
- **Location:** `src/lib/rateLimit.ts` and its 8 users (table order, pay, request, cancel, card delete request, bridge…)
- **Issue:** each serverless instance has its own memory, and instances come and go, so the limits are soft (the file says so). They slow a single tab, not a script.
- **Recommended fix:** move the public ones to the database counter from S1, or a Vercel Firewall rule per path.

### S6. No security headers
- **Severity:** Medium
- **Location:** `web/next.config.ts` (no `headers()`), no `src/proxy.ts`
- **Issue:** no `Content-Security-Policy`, no `frame-ancestors` / `X-Frame-Options` (the owner app can be framed for clickjacking), no `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`.
- **Recommended fix:**
  ```ts
  async headers() {
    return [{ source: "/(.*)", headers: [
      { key: "X-Frame-Options", value: "DENY" },
      { key: "X-Content-Type-Options", value: "nosniff" },
      { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
      { key: "Permissions-Policy", value: "camera=(self), microphone=(), geolocation=()" },
      { key: "Content-Security-Policy", value: "default-src 'self'; img-src 'self' data: https://*.supabase.co; frame-ancestors 'none'; base-uri 'self'; form-action 'self' https://*.tap.company" },
    ]}];
  },
  ```
  Start the CSP as `Content-Security-Policy-Report-Only`, check the pages, then enforce it.

### S7. Sessions cannot be revoked
- **Severity:** Medium
- **Location:** `src/lib/staffAuth.ts` (`makeSessionValue`, `readSession`), `api/staff/logout`
- **Issue:** sign-out only deletes the cookie. A copied cookie works for 12 hours unless the person is deactivated. There is no "sign out everywhere" after a lost phone or a PIN change.
- **Recommended fix:** add `session_version int not null default 1` to `staff_users`, put it in the signed payload, compare it in `loadStaff`, and bump it on sign-out-everywhere, PIN change and role change.

### S8. One secret signs everything, and it falls back to the database key
- **Severity:** Medium
- **Location:** `src/lib/staffAuth.ts`, `src/lib/pin.ts`, `src/lib/table/sentOrders.ts` (`STAFF_SESSION_SECRET ?? SUPABASE_SERVICE_ROLE_KEY`)
- **Issue:** if `STAFF_SESSION_SECRET` is ever removed, sessions and PIN hashes silently switch to the service-role key, and every PIN stops working. Rotating the database key would do the same. Keys are domain-separated, which is good.
- **Recommended fix:** in production require `STAFF_SESSION_SECRET` (at least 32 characters) and fail at start-up without it. Keep the fallback for local work only.

### S9. A reward can be redeemed by anyone who knows a 4-digit card code
- **Severity:** Medium
- **Location:** `src/app/api/staff/card/route.ts`, `staff/redeem/route.ts`
- **Issue:** staff can look a guest up by typing the code. A guest who overhears or guesses another code can ask the till to redeem that person's reward. The staff screen shows only a first name, so it is easy to miss.
- **Recommended fix:** allow redeem only after a QR scan (the QR carries the card), or ask for the last 2 digits of the guest's mobile when the code was typed by hand.

### S10. The CALABOS bridge is one long-lived, powerful token
- **Severity:** Medium
- **Location:** `src/lib/devChat.ts` `bridgeVenue()`, `src/lib/calabosAdmin.ts` (`give_pin`, `add_member`, `add_business`)
- **Issue:** a static bearer token can add businesses and hand out PINs in plain text. There is no expiry, rotation date or IP restriction, and the limit is in-memory.
- **Recommended fix:** rotate it every 90 days, add an allow-list (for example the Tailscale exit address), and make `give_pin` return a one-time link instead of the PIN.

### S11. CSRF rests on SameSite=Lax alone
- **Severity:** Low
- **Location:** all state-changing routes (`request.json()` without a Content-Type or Origin check)
- **Issue:** fine in today's browsers, but there is no second layer.
- **Recommended fix:** in `src/proxy.ts`, reject POST/PATCH/DELETE to `/api/*` (except the Tap webhook, POS and bridge) when `Origin` is not the site's own.

### S12. Vulnerable libraries through passkit-generator
- **Severity:** Medium
- **Location:** `package.json` → `passkit-generator@3.6.1` → `node-forge@1.4.0`, `joi@17.13.4` (`npm audit`: high)
- **Issue:** the node-forge advisory is about RSA signature *verification*; the app only signs passes, so the real exposure is low. The joi issues need attacker-shaped schemas or messages. Still, they will show up in any customer's security review.
- **Recommended fix:** add `"overrides": { "node-forge": "<patched version from GHSA-86w9-cpqp-85rv>", "joi": "^17.13.9" }`, run the Wallet pass tests, and move to a passkit-generator release that ships them.

### S13. CSV formula guard misses two characters
- **Severity:** Low
- **Location:** `src/app/api/owner/export/route.ts` `cell()`
- **Issue:** it escapes values starting with `= + - @`, but not a leading tab or carriage return (OWASP list).
- **Recommended fix:** `/^[=+\-@\t\r]/`.

### S14. Database function settings
- **Severity:** Low
- **Location:** `supabase/migrations/0002_ledger.sql` `apply_ledger()`
- **Issue:** no fixed `search_path` (advisor `function_search_path_mutable`), and `anon` / `authenticated` may EXECUTE it.
- **Recommended fix:**
  ```sql
  alter function public.apply_ledger() set search_path = public;
  revoke execute on function public.apply_ledger() from anon, authenticated, public;
  ```

## 3. Database and data integrity

### D1. Owner numbers, CSV export and guest search stop at 1000 / 500 rows
- **Severity:** High
- **Location:** `src/app/api/owner/summary/route.ts` (cards, 30 days of ledger), `owner/export/route.ts`, `owner/guests/route.ts` (`.limit(500)`, then search filtered in JavaScript)
- **Issue:** Supabase returns at most 1000 rows per request. Past 1000 members, "members", "points held", "visits this week" and the CSV are silently wrong. The guest search cannot find anyone outside the 500 most recent. `pointsSummaryDb.ts` and `serviceReport` already page correctly, so the fix exists in the code base.
- **Recommended fix:** count in SQL, and search in SQL:
  ```sql
  create function owner_summary(p_venue uuid, p_today timestamptz) returns jsonb
  language sql stable security definer set search_path = public as $$
    select jsonb_build_object(
      'members', (select count(*) from cards where venue_id = p_venue),
      'points_held', (select coalesce(sum(points),0) from cards where venue_id = p_venue),
      'visits_7d', (select count(*) from ledger l where venue_id = p_venue and kind = 'earn'
                    and created_at >= p_today - interval '6 days'
                    and not exists (select 1 from ledger u where u.undoes = l.id)));
  $$;
  ```
  Guest list: `.or(\`code.eq.${q},members.name.ilike.%${q}%\`)` with `.range()` paging. Export: loop with `.range()` the way `fetchAll` in `pointsSummaryDb.ts` does.

### D2. Erasing a guest deletes their points history
- **Severity:** Medium
- **Location:** `0001_init.sql`: `ledger.card_id … on delete cascade`, `src/lib/privacyDb.ts` `eraseCard()`
- **Issue:** a PDPL erasure removes the ledger rows, so past rewards and visits vanish from the reports, and once VAT receipts exist (build item 3) the sale records go with them.
- **Recommended fix:** erase the *person*, keep the *numbers*: blank the member's name, phone and email, set `deleted_at`, and keep the card and ledger rows (they hold no personal data). Change the foreign key to `on delete restrict` so a cascade can never wipe money records.

### D3. "One card per guest" is checked in code only, without an index
- **Severity:** Medium
- **Location:** `src/lib/cards.ts` `hasCardAt()` (added today), `members` (no index on `phone` / `email`)
- **Issue:** two joins at the same instant can both pass the check. Each check scans all members.
- **Recommended fix:**
  ```sql
  create index members_phone_idx on members (phone) where deleted_at is null;
  create index members_email_idx on members (lower(email)) where deleted_at is null;
  ```
  Then do the check and insert in one database function holding `pg_advisory_xact_lock(hashtext(venue_id || contact))`.

### D4. Unindexed foreign keys
- **Severity:** Low (now), Medium (at volume)
- **Location:** 18 foreign keys (advisor `unindexed_foreign_keys`); the ones on hot paths are `cards.member_id`, `orders.table_id`, `table_requests.table_id`, `audit_log.venue_id`, `staff_users.venue_id`
- **Issue:** joins and cascades on these scan whole tables as data grows.
- **Recommended fix:** `create index concurrently` on those five now; the rest when their tables grow.

### D5. Migration history is not recorded in Supabase
- **Severity:** Low
- **Location:** live project: migrations 0001–0011 were run in the SQL editor; only 0012 and 0013 appear in `list_migrations`
- **Issue:** you cannot tell from the database which files have run, so the next person may run one twice.
- **Recommended fix:** back-fill the migration table once (`supabase migration repair --status applied 0001 … 0011`), then only apply through migrations.

**Good already:** points move inside `security definer` functions with `select … for update` row locks, a 10-minute undo window, a unique undo per entry, idempotent POS receipts (`ledger_external_ref_idx`), and one open tab per table (`tabs_one_open_per_table`).

## 4. Performance and scalability

### P1. Owner summary reads every row into memory
- **Severity:** Medium
- **Location:** `src/app/api/owner/summary/route.ts`
- **Issue:** every load of the owner home pulls all cards and 30 days of ledger rows to the server, then counts in JavaScript. With 10,000 guests that is megabytes per click (and wrong past 1000, see D1).
- **Recommended fix:** the SQL function in D1. One small JSON answer.

### P2. The staff board makes 2 extra queries per open table, every 4 seconds
- **Severity:** Medium
- **Location:** `src/lib/table/db.ts` `readBoard()` (`tabIds.map(… tabMoney … payingNow …)`), `src/app/staff/board/Board.tsx` (`POLL_MS = 4000`)
- **Issue:** with 20 open tables and 3 staff phones that is about 30 database queries a second for one venue, before any guest polling. The guest table page adds about 7 queries every 5 seconds per phone (`TableApp.tsx`, `POLL_MS = 5000`).
- **Recommended fix:** one SQL view or function that returns the board in a single query (orders, lines, money per tab). Then switch both screens to Supabase Realtime on `orders` / `table_requests` for the venue, keeping a 30-second poll as a fallback.

### P3. Regions
- **Severity:** Low
- **Location:** `web/vercel.json` (`fra1`), Supabase `eu-central-1`
- **Issue:** good that both are in Frankfurt (no extra hop between them). Guests in Bahrain are about 100 ms away each way, felt on every tap. Guest data also leaves Bahrain, which the PDPL allows only under its transfer rules.
- **Recommended fix:** write down the PDPL transfer basis now. Check whether Supabase and Vercel offer a region in AWS `me-south-1` (Bahrain) or `me-central-1` (UAE) before the first big customer. I have not confirmed they do.

### P4. Base64 photos travel inside JSON
- **Severity:** Low
- **Location:** `src/app/api/owner/menu/photo/route.ts`, `src/lib/table/photo.ts` (600 KB cap)
- **Issue:** a 600 KB photo becomes about 800 KB of JSON and passes through the function's memory.
- **Recommended fix:** a signed upload URL straight to Supabase Storage, then a small "confirm" call that checks the bytes.

## 5. Error handling, logging and resilience

### E1. No error pages and no error tracking
- **Severity:** Medium
- **Location:** `src/app/` (no `error.tsx` or `global-error.tsx`); no Sentry or OpenTelemetry; 38 `console.error` calls only
- **Issue:** a crash on a guest page shows Next's bare error screen. Errors are kept only in Vercel's runtime logs, and on the Hobby plan those are kept **1 hour** (confirmed today when the log API refused a 2-hour window). After a busy evening nobody can see what failed.
- **Recommended fix:** add `app/error.tsx` and `app/global-error.tsx` in the Orbyn look with a retry button. Add Sentry (`@sentry/nextjs`) or Vercel Observability. Move to Vercel Pro before the first paying venue: log retention, plus Hobby is not meant for commercial use.

### E2. Many errors are swallowed on purpose; some should be logged
- **Severity:** Low
- **Location:** 71 `.catch(() => …)` / `catch {}` sites, for example `api/staff/login` (`signIn(...).catch(() => null)` turns a Supabase outage into "Wrong email or password"), `pin-login`
- **Issue:** most are right (a payment must not fail because of points), but some hide outages behind misleading messages.
- **Recommended fix:** in sign-in, tell "wrong password" apart from "service unavailable" (log it and answer 503). Leave the deliberate ones, but each should log once.

### E3. A not-found page still answers HTTP 200
- **Severity:** Low
- **Location:** `src/app/not-found.tsx` with `instant = false` (streamed); live `/card/<unknown>` returns 200
- **Issue:** monitors and search engines see success; the page itself is correct.
- **Recommended fix:** check unknown ids before streaming starts (for example in `generateMetadata`), or accept it and filter on the page's title in monitoring.

### E4. No health check or uptime alert
- **Severity:** Low
- **Location:** none
- **Issue:** if Supabase is paused or a key expires, the first person to know is a guest.
- **Recommended fix:** `GET /api/health` that runs `select 1` and returns 200/503, watched by an uptime monitor that alerts Saad's phone.

**Good already:** owner and staff route wrappers catch and log; ledger rule errors are shown in plain words; Wallet refresh and point awarding never break a payment; the webhook answers 502 so Tap retries.

## 6. Code quality, testing and maintainability

### Q1. CI does not run the production build
- **Severity:** Medium
- **Location:** `.github/workflows/ci.yml` (lint, typecheck, test; no `next build`)
- **Issue:** build-only failures reach `main`. Today the new not-found page passed lint, typecheck and all tests, and still broke `next build` (prerender rule). Only a manual build caught it.
- **Recommended fix:** add `- run: npm run build` with dummy env values, and `npm audit --omit=dev --audit-level=high` as a non-blocking step.

### Q2. No end-to-end tests and no coverage figure
- **Severity:** Medium
- **Location:** `tests/` (39 files, 556 tests: unit and route tests against an in-memory stand-in; `migrations.test.ts` uses PGlite)
- **Issue:** the route tests are good, but nothing clicks through a real browser, and the stand-in fakes some database behaviour (defaults, 1000-row cap, triggers). Bug D1 cannot show up in these tests by design.
- **Recommended fix:** a small Playwright suite on the local test copy: join → card → staff earn → redeem; table order → cancel → board → close cash. Run the database tests against PGlite with the real migrations instead of the stand-in where possible. Add `vitest --coverage` and track the number.

### Q3. Large components
- **Severity:** Low
- **Location:** `src/app/t/[code]/TableApp.tsx` (400 lines), `owner/Offers.tsx` (378), `lib/table/db.ts` (367), `owner/Service.tsx` (324)
- **Issue:** fine today, but each mixes data fetching, state and layout.
- **Recommended fix:** split `TableApp` into `Menu`, `Rounds` and `PaySheet`, with a `useTable(token)` hook for polling and actions. Split `db.ts` into `board.ts`, `orders.ts` and `menu.ts`.

### Q4. Repeated small helpers
- **Severity:** Low
- **Location:** `must()` in `table/db.ts`, `table/points.ts` and others; UUID regex in `cards.ts`, `points.ts`, `sentOrders.ts`, `TableApp.tsx`; the QR SVG builder in `Service.tsx`, `Guests.tsx` and `qr-kit/page.tsx`; client IP read in `pin-login` and `rateLimit.ts`
- **Recommended fix:** one `src/lib/util.ts` (`must`, `UUID`, `clientIp`) and one `<QrSvg url>` component.

### Q5. Lint warnings and casts
- **Severity:** Low
- **Location:** 7 lint warnings (for example `components/PinPad.tsx` missing hook dependency, `lib/assistant/parse.ts` unused `WORD`); 16 `as unknown as` casts, mostly on Supabase joins
- **Recommended fix:** fix the warnings and make CI fail on warnings. Generate database types (`supabase gen types typescript`) and type `db()` with them, which removes most casts.

**Good already:** `strict` TypeScript with no real `any`; zod on every input; comments explain why, not what; tests for cross-tenant access, the ledger, Tap, PINs, privacy and the table service.

## Strengths worth keeping

- No secrets in git; `.env.example` only; POS keys stored as SHA-256; PINs stored as keyed hashes.
- Per-screen session cookies (staff, owner, developer) signed with the screen name and compared in constant time.
- Points logic in the database with row locks, limits and an undo window.
- Tap webhook: signature check, then the charge is read back from Tap, so a forged call cannot mark anything paid.
- Uploads checked by their first bytes, size-capped, stored under a random name.
- Guest data minimised: staff see a first name only; the owner list hides phone and email; every export is logged.
- Guest round-cancel uses a signed cookie, so another phone at the table cannot cancel your round.
