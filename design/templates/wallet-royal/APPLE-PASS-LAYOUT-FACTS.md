# Apple Wallet pass layout facts (research, 2026-10-16)
Tags: V = read on Apple's own page. 3P = third-party only. INF = inferred / not documented. Pages were read with WebFetch (a summarising reader), so wording is as returned.

## 1. Strip image: size and behaviour (V)
| Style | Strip? | Current size (HIG, PD): pt = @1x; px @2x / @3x | Old guide [ARCH], iPhone 6 era |
|---|---|---|---|
| storeCard | yes | 375 x 144 pt; 750x288 / 1125x432 px | 375x123 ("all other cases"); 320x110 (3.5" phone, square barcode) |
| coupon | yes | 375 x 144 pt; 750x288 / 1125x432 | 375x144 ("gift cards and coupons") |
| eventTicket | not in current HIG/PD (PD table: strip "NA") | background 343x503 pt, thumbnail 60-90 x 90 pt | strip 375x98 (320x84 old phones) |
| generic | no (logo, icon, thumbnail) | thumbnail only | same |
| boardingPass | no (logo, icon, footer) | footer 268x15 pt, airline only (old: 286x15) | same |
- Fill rule [ARCH, V]: "Images are scaled (preserving aspect ratio) to fill this allotted space. Images with a different aspect ratio ... are cropped after being scaled." So fill + crop, never fit. The crop anchor is not stated (INF: centred, matches what you see).
- Your case: 375x123 scaled to 144 high = x1.171, 439 pt wide, so 32 pt (7.3%) is cut per side. In SOURCE terms only the middle 320 pt of 375 is visible: 27 pt (82 px @3x) lost per side. This explains the clipped last letter. Fix = export 1125x432 (and 750x288), keep the wordmark well inside the middle.
- Position [PD, V]: "The primary field and strip image are in the same place on the pass. If you add any text in a primary field, it automatically appears over the strip image." [HIG, V]: "text can appear over strip images ... place important visual elements toward the bottom or trailing edge."
- [PASS, V] `suppressStripShine` default true (no shine). PD labels "375 by 144 pixels" but HIG says pt; HIG is right (3x file = 1125 px).
- Caveat (V, ambiguous): the PD availability table marks strip for coupon/store card as "< iOS 26". Not clear whether iOS 27 changes store-card rendering: test on iOS 27.

## 2. storeCard fields, text baked into the strip
- Max counts [ARCH, V]: header up to 3; primary 1; coupons/store cards/generic with a square barcode: secondary + auxiliary "a total of up to four ... combined"; [SC, V]: "up to four secondary and auxiliary fields, all displayed on one row"; visible number depends on text length. Back fields: "as many fields as you need" [SC].
- No primary field? No Apple page marks any field group as required (INF: allowed, not stated). Strip + barcode only: not documented anywhere I found; test on device.
- Baking text: HIG (V) "Avoid embedding text in the strip image." and under Pass images: "Embedded text isn't accessible and may not be visible if images don't display on all devices. For text information, use text fields and semantic tags instead." It is a guideline ("avoid"), not a hard technical rule I could find. Downsides: V = not accessible (VoiceOver), Apple Watch never shows the strip [SC]. INF = not searchable/localised unless you ship per-language images (Apple supports localised images in .lproj folders), a changed value (points) needs a new image rather than a field update, change messages and lock-screen text need real fields. A brand wordmark as art is the grey area; name, code and points should stay real fields.

## 3. Collapsed stack (V)
[ARCH] header fields "are the only field that is visible when the passes are stacked". [HIG] logo and logo text "remain visible when the pass is collapsed"; header fields too. So: logo + logoText + header fields. Not the strip, not primary/secondary, not the barcode.

## 4. Barcode
- V: generated by Wallet from `message` + `format`; "Don't include any barcodes in images" [PD]. Formats QR, PDF417, Aztec, Code128 (+ Code39, Codabar, EAN-13, ITF) [BC]. `altText` = "text to display near the barcode" [BC]; not shown on watchOS. Rectangular codes are rotated on Watch; QR recommended [ARCH]. Square vs rectangular code changes the field layout (see 2).
- NOT documented by Apple: barcode size, panel colour, position. "Always on a white panel" is INF/observed only. I found no pass.json key for it. Dynamic/rotating QR: Apple DTS (https://developer.apple.com/forums/thread/748463): "not supported"; updates only through pass updates, which users can opt out of. iOS 27 [BC]: several barcodes may be listed as fallbacks.

## 5. Colours (V)
`backgroundColor` = background of front and back, ignored if a background image exists [ARCH]; `foregroundColor` = values of fields on the front; `labelColor` = labels on the front, system picks if omitted [PASS]. `footerBackgroundColor` only for poster EVENT tickets [PASS]. Per-field colour/font: none. [PFC] lists 13 keys (attributedValue, changeMessage, currencyCode, dataDetectorTypes, dateStyle, ignoresTimeZone, isRelative, key, label, numberStyle, textAlignment, timeStyle, value): no colour, no font. `attributedValue` only allows `<a href>` links, and `textAlignment` is invalid for primary and back fields.

## 6. Change messages (V unless tagged)
`changeMessage` [PFC]: "format string for the alert text to display when the pass updates ... must contain the escape %@ ... You need to provide a value for the system to show a change notification" (not used on watchOS). [UPD]: "If the value of a field has changed and the field specifies a change message, the device shows the message". PFC is the parent of header, primary, secondary, auxiliary, back and additionalInfo fields, so a BACK field can carry it (structural, V). Apple does not say "lock screen" in these pages. 3P (help.passkit.com): back-field messages work; same value again = no alert. HIG: change messages only for time-critical info, "Never use a change message for marketing". Needs a web service + APNs push to deliver an update [Adding a Web Service page].

## 7. Poster generic (iOS 27) (V unless tagged)
- iOS/watchOS 27+ only; key `posterGeneric` [PO]. Fallback: add a second style dictionary (`storeCard`, `generic`...): "newer devices display the generic pass with the poster, and older devices display the legacy style they recognize" [PO]. Pass Designer needs macOS 27 [PD].
- Artwork `artwork.png` 358 x 448 pt, PORTRAIT, unblurred; a material strip covers the bottom edge; header area at top; barcode + footer below [HIG]. Fields [PO]: header field, up to four primary, two footer (WWDC26 says only the first footer is shown), back fields, additional info, square QR. Primary logo 30 pt high, 30-126 wide [HIG] (PD table says "Logo iOS 27+": unclear). `footerBackgroundColor` is for poster event tickets only.
- Landscape: not addressed by Apple; the only stated size is portrait 358x448. NOT verified that a landscape card is supported. A landscape card drawn INSIDE the portrait art is possible (INF).

## 8. Google Wallet (short)
- heroImage "displayed at 100% width" ([loyaltyclass ref](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyclass)). Size conflict: loyalty brand guidelines page says 1032x812 (about 5:4), PNG, 20dp padding top/bottom, "Don't embed text ... won't be localized" ([guidelines](https://developers.google.com/wallet/retail/loyalty-cards/resources/brand-guidelines)); 3P and Google's offers page (search snippet) say 1032x336 (3:1). Test in the Pay and Wallet Console preview.
- Logo: 660x660 min, 1:1, masked into a circle, keep 15% margin; wide logo 1280x400 (16:5) replaces the logo top left. Text on the hero: not forbidden, discouraged.
- Notification ([push page](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications)): addMessage with TEXT_AND_NOTIFY, or update with notifyPreference=notifyOnUpdate (allowlisted fields: points balance, tier, program name). Max 3 per pass per 24 h; user must have notifications on.

## Bonus (open item): Apple badge [https://developer.apple.com/wallet/add-to-apple-wallet-guidelines/]
V: "Do not create your own version of the badge"; "With very dark backgrounds, use the outline option"; use PKAddPassButton in apps.

## Recommendation for a landscape-credit-card look
Closest achievable: on every iPhone a storeCard with backgroundColor = the marble/black, a seamless 1125x432 strip (marble + gold Your Brand as brand art only, wordmark inside the central 320 pt), logo + logoText + a header field (points), secondary/auxiliary for name, QR below. On iOS 27+ add `posterGeneric` with a 358x448 pt artwork that contains a drawn landscape card (stay clear of the top header area and bottom material strip), with the storeCard as fallback; test both. Impossible: a true 1.586:1 card-shaped pass (the pass is always a tall rounded card), recolouring or moving the barcode panel, per-field fonts or colours, a live-updating image without a pass update, rotating QR codes. Keep name, code and points as real fields.
